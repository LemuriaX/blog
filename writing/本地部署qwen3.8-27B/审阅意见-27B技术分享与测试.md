1. **显存预算应统一为字节或 GiB。**

   [主文档第 5.3 节](E:/codex/技术分享修正前备份-20260905/27B模型如何塞进20GB显存-技术分享.md:370)直接计算“20.0 GB − 17.6 GB = 2.4 GB”，配图也使用相同口径。问题在于仓库文件的十进制 GB 与硬件监控的 MiB/GiB 尚未统一，文件大小也不等于加载后的 GPU 权重缓冲大小。

   例如，17.6×10⁹ 字节约为 16.39 GiB；如果后端报告的总显存为 20 GiB，两者相减约为 3.61 GiB。这只是单位换算示例，仍不是可供 KV 使用的实测余量。应先记录实际总显存字节数，再分别列出文件字节数、GPU 权重缓冲、KV、其他缓冲和系统占用。同步修改 [显存预算图](E:/codex/技术分享修正前备份-20260905/local-llm-sharing-assets/vram-budget.svg:24)，避免正文改了而图中仍保留 2.4 GB。

2. **把通用 KV 公式落实到这款模型，这是最值得补充的技术内容。**

   [第 6.2 节](E:/codex/技术分享修正前备份-20260905/27B模型如何塞进20GB显存-技术分享.md:421)已经提醒混合注意力的特殊性，但停留在“部分层增长”。可以进一步解释：64 个语言模型层中，16 层是 Full Attention；其 KV heads 为 4，head dimension 为 256。其余层的 recurrent/SSM 状态需要另外计算。[官方配置](https://huggingface.co/Qwen/Qwen3.8-27B/blob/main/config.json)。

   在单序列、只计算这 16 个 Full Attention 层的 K/V 存储时，可得到下面的理论表：

   | 分配的 Token 容量 | F16 K/V | Q8_0 K/V | Q4_0 K/V |
   |---:|---:|---:|---:|
   | 8,192 | 0.50 GiB | 0.266 GiB | 0.141 GiB |
   | 32,768 | 2.00 GiB | 1.063 GiB | 0.563 GiB |
   | 65,536 | 4.00 GiB | 2.125 GiB | 1.125 GiB |
   | 131,072 | 8.00 GiB | 4.250 GiB | 2.250 GiB |

   计算式为 `T × 16 × 4 × 256 × 2 × 每元素字节数`。F16 为 2 字节；Q8_0 每 32 个元素占 34 字节；Q4_0 每 32 个元素占 18 字节，已经计入块缩放参数。[GGML 格式定义](https://github.com/ggml-org/llama.cpp/blob/master/ggml/src/ggml-common.h)。

   这张表必须标为理论存储估算，不包含 recurrent/SSM 状态、额外快照、对齐、计算缓冲、权重和系统占用，也不证明某后端支持相应量化 KV。引擎可能在加载时预分配 KV，因此需要区分“配置容量”与“实际输入长度”。并发公式中的 T 也应说明是每序列容量还是共享池总容量，避免重复乘并发数。

4. **“64 层模型”不能直接转换成“gpu_layers=64 就是全部 GPU Offload”。**

   [第 11.3 节](E:/codex/技术分享修正前备份-20260905/27B模型如何塞进20GB显存-技术分享.md:817)与两个启动脚本采用这一假设。llama.cpp 的卸载计数还涉及 output layer；当前实现的全卸载计数使用 `n_layer_all + 1`。具体哪些张量留在 CPU、是否有额外层及包装器如何映射，取决于实际后端版本。[llama.cpp 模型加载实现](https://github.com/ggml-org/llama.cpp/blob/master/src/llama-model.cpp)。

   应使用当前 Unsloth 版本明确支持的全卸载设置，并用启动日志中的实际卸载结果、CPU/GPU 权重缓冲及缓存位置确认。不能仅用状态接口返回的请求层数作为证明，也不能简单把所有版本都硬编码为 65。正常的 CPU 元数据或 staging buffer 也不等于主要权重在 CPU 推理。

3. **Thinking 测试的 1,024 Token 上限需要单独验证。**

   [质量参数](E:/codex/技术分享修正前备份-20260905/Qwen3.8-27B上下文与性能测试方案.md:175)开启 Thinking，却没有固定 effort，且最大输出仅为 1,024。推理可能用完预算而尚未输出最终 JSON，此时评分下降反映的是预算耗尽，不应直接解释为量化质量下降。

   先固定 effort，观察 `finish_reason` 与最终回答是否生成。将 `budget_exhausted` 单独统计；若增加生成预算，必须同时满足 `完整 prompt_tokens + max_tokens ≤ 实际上下文容量`，长文任务需要相应减少输入或提高容量。不要仅增加 max_tokens 而保留原有 6,800 Token 输入和 8K 窗口。

4. **长上下文检索应增加干扰和无答案样本，并测量真正的 Token 位置。**

   [生成器](E:/codex/技术分享修正前备份-20260905/context-benchmark/generate_context_cases.py:185)直接告诉模型“共有五条校验记录”“其余记录不包含答案”，五条答案又有唯一的醒目标记。这能验证简单检索，但不足以代表长文理解。

   可以加入同类记录、相似项目名、历史失效值、重复修订及缺失答案，也可增加跨段关联问题。保留一组简单 needle 题用于确认基础容量。现在的 10%～90% 按记录条数定位，属于近似位置；如果要展示位置召回曲线，应保存实际 Token 偏移、比例、上下文长度及模板版本。

5. **把配置容量、已验证输入长度、任务效果和稳定性分开报告。**

   [128K 档](E:/codex/技术分享修正前备份-20260905/Qwen3.8-27B上下文与性能测试方案.md:125)实际目标输入是 116,000 Token，输出最多 192。因此可以报告“配置 131,072、在约 116,000 Token 输入下通过”，不能据此说测到了接近 131,072 的有效输入上限。

   需要摸清边界时，增加保留输出空间的接近上限用例；也可在最后成功档与失败档之间增加中间档。三个文档、共 15 个校验点只适合作为初步筛查，不适合推断稳定的 90% 召回能力。15 个点下“至少 90%”实际要求至少 14/15，且五个位置来自同一文档，相互并不独立。

   8K 可以复用 Q3 配置的共同性能结果，但要再应用与容量测试相同的正确率和位置规则，并将它放入容量汇总，不能只用共同性能的“通过”。

6. **让性能与硬件数据的采集更可比较。**

   当前性能统计是三个不同合成样本各跑一次的中位数，包含输入差异和运行波动。若要说明波动，增加同一输入的重复次数，保持不同配置使用相同样本顺序，或使用固定种子随机化顺序。

   正式测速可加入同量级输入的预热，预热结果不计入统计；生成速度测试需要足够长且相近的实际输出，192 只是上限，模型可能提前结束。少量样本报告中位数及范围，不宜展示看似精确的高分位延迟。

   分别采集模型加载后、Prefill 和 Decode 的显存/内存。HWiNFO 每秒采样得到的是采样峰值，短时尖峰可能遗漏；报告应写清采样周期。若关注能耗，使用平均功率或积分能量，并与同一请求时间对齐，峰值功耗不能代表完成任务的能耗。

**最后看脚本：下面列出会改变结果解释或损失证据的问题，优先处理前六项。** P1 表示正式采集数据前应修复；P2 表示影响解释、复现或维护，建议在结果发布前处理。

1. **[P1] 请求超时可能使已经完成的结果全部丢失。**

   位置：[长上下文 runner](E:/codex/技术分享修正前备份-20260905/context-benchmark/run_context_benchmark.py:550)、[质量 runner](E:/codex/技术分享修正前备份-20260905/context-benchmark/run_profile_benchmark.py:620)。

   捕获范围仅为 `RuntimeError / ValueError / JSONDecodeError`。流式读取的 `TimeoutError`、部分连接中断或不完整响应异常可能直接穿透，而 CSV 到所有请求结束后才写。离线模拟第一条成功、第二条抛出 TimeoutError，主函数直接退出，输出文件从未打开。

   建议统一转换并分类传输异常；每个请求开始时记录请求 ID，完成或失败后立即追加 JSONL/CSV 并 flush；退出时再从已落盘记录生成摘要。给长请求增加总耗时上限，区分连接超时、读取超时和整个请求的截止时间。失败重试应作为新 attempt 留痕，不能替换第一次失败。

2. **[P1] 流式响应缺少正常结束标记时仍被当成普通结果返回。**

   位置：[SSE 读取函数](E:/codex/技术分享修正前备份-20260905/context-benchmark/run_context_benchmark.py:166)。

   循环读到 EOF 就结束，没有验证是否收到了正常终止事件。离线模拟只有一条内容与 usage 事件、没有 `[DONE]` 和 `finish_reason`，函数仍返回完整结果对象。若 usage 和答案恰好已经到达，后续通过规则也不检查正常终止，存在误判可能。

   建议按锁定后端的协议验证终止事件，保存 `stream_complete`；将输入截断、输出达到 max_tokens、传输中断分为独立状态。容量判定和性能有效性判定都要使用这些状态。`finish_reason=length` 应记录为输出预算到顶，其是否允许进入某个吞吐量实验由该实验规则明确决定。

3. **[P1] 质量汇总排除运行失败，容易产生过高分数。**

   位置：[build_task_summaries](E:/codex/技术分享修正前备份-20260905/context-benchmark/run_profile_benchmark.py:437)。

   前四项得分只在 `valid_rows` 上取中位数。离线复现：一次正确、两次运行失败，最终为 8/10。虽然 JSON 中保留了 `successful_runs=1, total_runs=3`，质量 Markdown 表和顶层平均分没有展示成功率。

   建议以计划执行数为分母报告运行成功率、任务成功率；样本不足时标为“不完整”。内容质量可以在已完成回答上另算，但不能直接作为整套配置的可靠性结论。把失败次数和有效样本数放进所有摘要。

4. **[P1] 评分对格式的权重过高，错误答案也能获得 7/10。**

   位置：[score_json_answer](E:/codex/技术分享修正前备份-20260905/context-benchmark/run_profile_benchmark.py:168)、[stability_score](E:/codex/技术分享修正前备份-20260905/context-benchmark/run_profile_benchmark.py:234)。

   对任务 A 三次返回 `{"bytes":1,"GB":1,"GiB":1}`，正确性为 0，完整性、指令遵循、可验证性各 2 分，重复错误答案再得到 1 分稳定性，合计 7/10。它符合当前评分实现，却与“质量分”的通常理解冲突。

5. **[P1] 配置校验不足以证明实验条件生效。**

7. **[P2] 运行状态和自动判定仍有脱节。**

   位置：[Python 正常退出](E:/codex/技术分享修正前备份-20260905/context-benchmark/run_context_benchmark.py:564)、[容量状态赋值](E:/codex/技术分享修正前备份-20260905/context-benchmark/run_all_contexts.ps1:372)、[顶层失败收集](E:/codex/技术分享修正前备份-20260905/context-benchmark/run_full_benchmark.ps1:636)。

   单条请求失败被写入 error_row 后，Python 仍返回 0；容量脚本随后将阶段和 itemStatus 记为 success。verdict 虽然为 fail，但 failed_stage/error 可能为空。共同性能判定未通过也不会加入 failedProfiles；质量任务全部失败时，也可能生成平均分为 0 的正常摘要并被标成“完成”。

   可以保留“执行结束”和“判定通过”两种状态，但应另外输出 `completed / partial / failed`、失败原因、有效样本数。质量不达标或高容量 OOM 是合法实验结果，不必一概视为工具错误；传输失败、协议不完整和配置无效应明确区分。清理进程失败时也应先保存当前状态与总摘要。

9. **[P2] 环境记录中 AdapterRAM 无法正确表达 20GB 级显存。**

   位置：[环境采集](E:/codex/技术分享修正前备份-20260905/context-benchmark/run_full_benchmark.ps1:332)。

   `Win32_VideoController.AdapterRAM` 是以字节计的 uint32，不能表示 20GB 级容量，因此 `adapter_ram_bytes` 不能用于验证这张显卡的实际显存。[Microsoft 定义](https://learn.microsoft.com/en-us/windows/win32/cimwin32prov/win32-videocontroller)。应从能报告 64 位容量的 GPU API、后端或监控工具记录容量及来源。

   相邻的 `TotalVisibleMemorySize / 1MB` 实际得到 GiB 口径，字段却名为 `system_memory_gb`，也应统一单位。
